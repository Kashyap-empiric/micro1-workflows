Set the production-usage window to the 7 full days ending the day before the run, all times in UTC. Every Supabase query in this run stays inside that window.

Across all four repos, find every hardcoded or templated LLM prompt string, whatever form it takes in that codebase's language and SDK: raw role/content dicts, LangChain SystemMessage or PromptTemplate objects, a plain string constant passed straight into an HTTP call body, a Dart string sitting inside a FlutterFlow custom action, whatever's actually there. Don't limit yourself to one detection pattern, a prompt with no framework around it at all counts just as much as one wrapped in a named SDK class.

Group what you find into prompt families by what the prompt is actually for rather than its filename or variable name: a support chatbot persona, an internal ticket or thread summarizer, a code review assistant, a receipt or data extractor, and whatever else genuinely shows up. Two prompts belong to the same family when they're doing the same job for the product even if the wording, formatting, or which model they target has drifted apart, that's the whole point of this check. A prompt that only exists in one codebase, with nothing to compare it against, still gets reported, just noted as single-source rather than drifted.

For each family that shows up in more than one codebase, treat whichever platform has the most recently modified version (by commit date) as canonical. If two platforms tie on that, the Python backend wins the tie. Rate every other platform's version against canonical on a simple three-way scale: identical (word for word, ignoring whitespace), minor drift (wording or formatting changed but the instruction and intent are the same), or meaningfully diverged (the instruction, tone, examples, or output format actually changed). Say specifically what changed for anything rated minor or meaningful, don't just assign the label.

Cross-reference prompt_invocation_logs for the window above to check what's actually running in production per platform instead of just what's sitting in the repo. A platform's code can carry an updated prompt that production logs show it isn't actually serving yet (still tagged with an older version), call that out explicitly since it's a different problem than wording drift, code says one thing, production is doing another. A platform with zero logged invocations for a family in the window gets noted as no observed production traffic rather than skipped.

For every model actually targeted by a prompt (check both the code and the logs' model_used field), look up that model's current, officially documented recommended prompting pattern via Web Search, structured output support, system role handling, message format, whatever's relevant, and flag any prompt leaning on a workaround the model doesn't need anymore, like manually instructing "reply only in JSON, no other text" when the provider now offers a native structured output mode. Note the source and date for whatever you found.

Some versions will trip both checks at once: a wording or format divergence from canonical and a deprecated model-pattern flag on that exact same platform's version. Don't let one flag swallow the other. Report both findings for that version, and don't wave off the divergence as 'just' outdated prompting technique, or the deprecated pattern as 'just' wording drift. When a double-flagged version drives a Jira ticket, keep the wording fix and the pattern fix as two separate, clearly labeled action items instead of one merged line.

Open a Jira ticket in "Cahuu Prompt Governance" (CPG) for any prompt family with at least one platform rated meaningfully diverged from canonical, or with a confirmed deprecated-pattern flag on any of its versions.
